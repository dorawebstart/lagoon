## Мої питання

### Навіщо нам Visual Studio (Build Tools)?
Повна Visual Studio не потрібна — встановлено лише **Build Tools** (компілятор і лінкер без редактора, код пишемо у VS Code).
- Rust на Windows (toolchain `msvc`) компілює код сам, але **склеює** його в `.exe` лінкером Microsoft `link.exe`, який є лише в C++ Build Tools.
- Крейти `windows` і `tauri` викликають системні бібліотеки Windows (`user32.lib`, `kernel32.lib`…) з **Windows SDK**, що теж іде з Build Tools.
- Без них `cargo build` падає з помилкою `linker 'link.exe' not found`.

### Що таке hook (хук)?
**Hook** («гачок») — це місце, куди програма дає «причепити» свій код: «коли станеться подія X — виклич ось це».
У Claude Code hooks налаштовуються у `~/.claude/settings.json`. На кожну подію Claude Code сам виконує те, що там вказано:
- `UserPromptSubmit` — ти надіслав завдання;
- `PreToolUse` — Claude зараз запустить інструмент (Bash, Edit…);
- `PermissionRequest` — Claude просить дозволу;
- `Notification` — Claude чекає на тебе;
- `Stop` — Claude закінчив.

Hook може бути командою (скрипт) або, як у нас, **HTTP-запитом** (`"type": "http"`): Claude Code надсилає JSON з подією на `http://127.0.0.1:47823/hook`, острів його приймає. Для `PermissionRequest` Claude Code ще й **чекає відповіді** — так острів може сказати «дозволити» чи «відхилити».

Аналогія з вебу: як **webhook** у GitHub чи платіжних системах — «коли щось сталося, надішли POST на мою адресу».

### Як викликати Claude на острові? Я бачу тільки музику
Claude на острові — не лише для дозволів: ще «Працюю…», «Bash: git status», «Claude чекає на тебе», «Готово ✓». Але острів дізнається про Claude Code **лише після підключення hooks**:
1. Трей → **Налаштування** → **Скопіювати конфіг hooks**.
2. Відкрити `C:\Users\slayyya\.claude\settings.json`, вставити скопійоване поле `"hooks"` на верхній рівень (якщо `"hooks"` уже є — об'єднати).
3. Перезапустити Claude Code.

Після цього острів показує роботу будь-якого Claude Code на цьому комп'ютері.

### Чому 106 МБ, і що таке WebView2?
- У **Диспетчері завдань** Lagoon займає **~40 МБ** («Lagoon (4)») — це показник «приватний робочий набір», його бачить користувач. Критерій MVP «< 100 МБ» виконано.
- 106 МБ — інша, суворіша метрика (*private bytes*): уся пам'ять, яку процеси зарезервували, включно з тією, що Windows уже вивантажила з оперативної.
- **WebView2** — рушій браузера Microsoft Edge (Chromium), вбудований у Windows. Tauri показує наш HTML/CSS/JS у «міні-браузері» всередині вікна. Як і Chrome, він має кілька процесів:
  - **browser** — головний, керує рештою;
  - **renderer** — виконує нашу сторінку (JS, CSS); одне вікно = один renderer;
  - **gpu-process** — малювання (ми вимкнули відеокарту `--disable-gpu`, тож він маленький);
  - **utility** — мережа, сховище;
  - **crashpad** — збирає звіти про падіння.
- Сам `lagoon.exe` (наш Rust) — лише ~6 МБ.
- Плюс WebView2: він уже є в Windows, тому інсталятор важить 1,5 МБ. Програми на Electron (Discord, VS Code) несуть свій Chromium — ~100 МБ інсталятора і більше пам'яті.
- Що ми зробили, щоб зменшити пам'ять (208 → ~106 МБ private bytes): вікно налаштувань створюється лише коли відкрите (мінус один renderer) і вимкнули GPU (GPU-процес 85 → 12 МБ).

### Що таке трей?
**Область сповіщень** у правому нижньому куті екрана, біля годинника. Там іконки програм, що працюють у фоні (звук, Wi-Fi, Spotify…). Частина ховається під стрілкою «^».
Іконка Lagoon у треї: **лівий клік** — налаштування, **правий** — меню «Налаштування / Перезапустити / Вийти». Її можна перетягнути з «^» на панель задач, щоб завжди була на виду.

### Ми дійшли до кінця роботи?
Так, **MVP (версія 0.1) завершено**: кроки 0–10 плану виконано, реліз `v0.1.0` опубліковано. Далі — версії 0.2–0.7 (issues #11–#22 на GitHub). Перед ними — розібратися з тим, що є на GitHub.

### Чому автозапуск перестав працювати після перенесення папки?
Автозапуск — це запис у реєстрі Windows (`HKCU\Software\Microsoft\Windows\CurrentVersion\Run`) з **повним шляхом** до exe. Він вказував на `C:\git_project_lagoon\src-tauri\target\release\lagoon.exe`, а папку перенесли. Рішення: встановити Lagoon з інсталятора і ввімкнути автозапуск у встановленій версії — тоді він не залежить від папки проєкту.

## Словничок

| Слово | Що означає |
|---|---|
| **Tauri** | фреймворк: вікно програми = WebView2 + бекенд на Rust |
| **invoke** | JS викликає Rust-команду: `invoke("назва", { аргументи })`, повертає Promise |
| **emit / listen** | Rust надсилає подію (`emit`), JS її слухає (`listen`) |
| **крейт (crate)** | бібліотека Rust (як пакет npm) |
| **Cargo** | менеджер пакетів і збирач Rust (як npm) |
| **GSMTC** | Windows API медіапанелі: що грає, кнопки ⏮ ⏯ ⏭ |
| **click-through** | кліки проходять крізь прозору частину вікна до програм під ним |
| **hook** | «гачок»: Claude Code викликає наш код на кожну подію |
| **трей** | область сповіщень біля годинника |
| **PR (pull request)** | запит на злиття гілки в `main` з описом і переглядом |
| **CI** | автоматичні перевірки на GitHub на кожен PR (`ci.yml`) |
| **реліз / тег** | тег `v0.1.0` позначає версію; `release.yml` збирає інсталятор і публікує його |

## Відповіді на питання для самоперевірки

### Крок 0 — Git і GitHub

**1. Чому в `.gitignore` є `src-tauri/target/`, і що там з'явиться після першої збірки?**
Там результати компіляції Rust: проміжні файли всіх крейтів, `lagoon.exe`, інсталятори. Це сотні мегабайт, які завжди можна перезібрати з коду, і вони різні на різних машинах. У git зберігають лише вихідний код.

**2. Навіщо працювати в окремих гілках `feat/…`, а не комітити все одразу в `main`?**
Щоб `main` завжди збирався і працював. Зміни спершу живуть у своїй гілці, проходять CI і перегляд у PR, і лише потім потрапляють у `main`. Якщо щось пішло не так — гілку просто не зливають.

**3. Чим `gh pr merge --squash` відрізняється від звичайного мержу?**
Squash «стискає» всі коміти гілки в **один** коміт у `main`. Історія `main` виходить чиста: один коміт = один крок плану. Звичайний мерж переносить усі проміжні коміти і додає коміт злиття.

**4. Де зберігатимеш токен для hooks, щоб він не потрапив у публічний репозиторій?**
У локальних налаштуваннях програми — `%APPDATA%\com.dorawebstart.lagoon\settings.json`. Ця папка поза репозиторієм. Токен генерується випадково при першому запуску.

### Крок 1 — каркас Tauri

**1. Чому `greet` приймає `&str`, а повертає `String`? Що сталося б, якби вона повертала `&str`?**
`&str` — позичене посилання: функції досить прочитати ім'я, забирати його не треба. Результат створюється **всередині** функції (`format!`), а все, що створено у функції, знищується, коли вона закінчується. Якби ми повернули `&str` на цей рядок, посилання вказувало б на знищені дані — компілятор Rust цього не дозволить (помилка про *lifetime*). Тому повертаємо `String` — віддаємо рядок у власність тому, хто викликав.

**2. Що станеться, якщо в JS викликати `invoke("hello")`, а команди `hello` немає в `generate_handler![...]`?**
Нічого не впаде: Promise у JS відхилиться з помилкою на кшталт «command hello not found». Rust-код при цьому не виконується.

**3. Навіщо `#![cfg_attr(not(debug_assertions), windows_subsystem = "windows")]`, і чому в dev ти все одно бачиш логи?**
У релізній збірці цей атрибут прибирає чорне вікно консолі поруч із програмою. У dev-збірці `debug_assertions` увімкнено, тож умова `not(...)` хибна, атрибут не застосовується — програма консольна, і логи видно в терміналі `npm run tauri dev`.

**4. Чим `devUrl` відрізняється від `frontendDist` у `tauri.conf.json`?**
`devUrl` (`http://localhost:1420`) — у режимі розробки Tauri бере сторінку з живого сервера Vite, зміни видно одразу (hot reload). `frontendDist` (`../dist`) — у релізі Tauri вшиває в exe вже зібрані файли.

**5. Що робить `.expect(...)`, і чому для справжніх помилок краще `?`**
`expect` при помилці зупиняє програму (*panic*) з повідомленням. `?` передає помилку тому, хто викликав функцію, щоб той вирішив, що робити — програма не падає. `expect` доречний лише там, де помилка означає, що далі працювати неможливо.

### Крок 2 — вікно-острів

**1. Що станеться, якщо прибрати рядок `mod window;` з `lib.rs`?**
Компілятор взагалі не побачить файл `window.rs`, і виклик `window::place_top_center` дасть помилку компіляції «unresolved module».

**2. Чому `primary_monitor()` повертає `Option`, а не просто `Monitor`? Що робить наш код у випадку `None`?**
Бо монітора може не бути (рідкісні випадки, наприклад сесія без дисплея). `Option` змушує обробити це явно. У випадку `None` функція просто повертає `Ok(())` — нічого не робить, вікно лишається, де було.

**3. Навіщо перетворювати `width` з `u32` на `i32`? Що могло б статися з `u32` на другому моніторі ліворуч?**
`u32` не буває від'ємним. Різниця «ширина екрана − ширина вікна» могла б стати від'ємною → у debug-збірці паніка (переповнення), у релізі — величезне число. А координати на моніторі ліворуч від основного **від'ємні** (`x = -1920`), тож для них потрібен знаковий `i32`.

**4. Чим `?` відрізняється від `.expect(...)`, і чому в `window.rs` ми використали `?`**
`?` повертає помилку нагору (у `setup`), а не зупиняє програму. Функція `place_top_center` не повинна вирішувати долю всього застосунку — це рішення того, хто її викликав.

**5. Чому `place_top_center` приймає `&WebviewWindow`, а не `WebviewWindow`?**
Функція лише ставить вікно на місце, забирати його не треба. Після виклику `lib.rs` ще користується вікном (`show()`, запуск потоку). Якби функція забрала вікно у власність, далі ним користуватися було б не можна.

### Крок 3 — click-through

**1. Навіщо `HitRegion` загорнуто в `Mutex`? Хто пише, хто читає?**
Пише команда `set_hit_region` (її викликає JS, коли змінюється розмір пігулки), читає фоновий потік, що кожні 30 мс перевіряє курсор. Це різні потоки, і без `Mutex` вони могли б одночасно писати й читати — дані зіпсувалися б. Rust без захисту такий код просто не скомпілює.

**2. Що буде, якщо прибрати `move` у `thread::spawn(move || ...)`?**
Замикання намагатиметься лише **позичити** `window`, а потік може жити довше, ніж функція, у якій ця змінна живе. Компілятор не дозволить: «closure may outlive the current function».

**3. Навіщо ділити координати курсора на `scale_factor`? Що зламається на 125% без цього?**
Курсор і вікно Windows дає у фізичних пікселях, а JS — у CSS-пікселях. На масштабі 125% один CSS-піксель = 1,25 фізичних. Без ділення зона пігулки «з'їхала» б: острів ловив би мишу не там, де його видно.

**4. Чому `ignoring != Some(should_ignore)`, а не виклик `set_ignore_cursor_events` кожні 30 мс?**
Щоб не смикати Windows API 33 рази на секунду без потреби. Режим змінюється рідко — викликаємо лише тоді, коли він справді змінився.

**5. Чому `contains` приймає `&self`, а `start_click_through` — `WebviewWindow` без `&`?**
`contains` лише читає прямокутник. `start_click_through` передає вікно в потік, який житиме весь час роботи програми, тому мусить забрати його у власність.

### Крок 4 — розкриття при наведенні

**1. Чому не CSS `:hover`, а подія з Rust?**
Коли вікно «прозоре для миші», сторінка не отримує **жодних** подій миші, тож `:hover` і `mouseleave` можуть «залипнути». Rust і так кожні 30 мс знає, де курсор, тому він — джерело правди.

**2. Чим `emit` (Rust → JS) відрізняється від `invoke` (JS → Rust)?**
`invoke` — JS викликає Rust-функцію і чекає результат (як `fetch`). `emit` — Rust оголошує подію, а всі, хто підписався через `listen`, її отримують; відповіді немає (як `dispatchEvent`).

**3. Навіщо `last_over`? Що, якщо надсилати `emit` кожні 30 мс?**
Щоб надсилати подію лише при зміні стану. Інакше фронтенд отримував би 33 події на секунду: зайва робота, а таймер згортання постійно перезапускався б.

**4. Що буде, якщо прибрати `let _ =` перед `window.emit(...)`?**
Скомпілюється, але з попередженням «unused `Result` that must be used». У нашому CI попередження clippy — це помилка (`-D warnings`), тож PR не пройшов би перевірку. `let _ =` явно каже: «результат мені не потрібен».

**5. Чому `start_click_through` перейменували на `start_cursor_watcher`?**
Бо функція тепер робить більше: не лише вмикає/вимикає click-through, а й повідомляє фронтенд про наведення. Назва має описувати, що функція робить.

### Крок 5 — трей, налаштування, UA/EN

**1. Чому `saved_language` повертає `String`, а не `&str`?**
Рядок береться з JSON-сховища і створюється всередині функції. Посилання на нього стало б недійсним після виходу з функції — тому віддаємо `String` у власність.

**2. Що зробить `match language { "en" => ..., _ => ... }`, якщо прийде `"de"`?**
Спрацює гілка `_` («усе інше») — меню буде українською.

**3. Навіщо `api.prevent_close()` для вікна налаштувань?**
У кроці 5 хрестик мав лише **ховати** вікно, а не знищувати: `prevent_close()` скасовує закриття, і ми викликаємо `hide()`. У кроці 10 це змінили: вікно тепер повністю закривається і створюється заново при відкритті — так менше пам'яті.

**4. Чому для замикання в `app.listen(...)` потрібні `move` і окрема копія `handle.clone()`?**
Замикання зберігається і викликається пізніше, з іншого потоку, тож має **володіти** всім, що використовує (`move`). Оригінальний `handle` після цього ще потрібен у `setup` (для медіа, сервера), тому в замикання передаємо копію.

**5. Що станеться, якщо JS надішле `settings:changed` без поля `language`? Чи впаде Rust?**
Не впаде. Поле `language: Option<String>` стане `None`, `if let Some(language)` не спрацює — меню трею просто не зміниться. Якщо JSON узагалі зламаний, `from_str` поверне `Err`, і ми його так само мовчки пропустимо.

### Крок 6 — media.rs

**1. Чому обробники подій Windows лише кидають сигнал у канал, а не читають стан самі?**
Обробники викликаються в службових потоках Windows, кілька поспіль і в довільному порядку. Якби кожен читав стан і робив `emit`, були б гонки та дублікати. Так уся робота відбувається в **одному** нашому потоці, по черзі, а обробники максимально короткі.

**2. Навіщо `thread::sleep(80 мс)` + `try_recv()`?**
Зміна пісні — це 3–4 події майже одночасно (назва, статус, позиція). Пауза і «вичерпування» каналу склеюють їх в одне оновлення. Без цього було б кілька читань стану і кілька подій у фронтенд за частку секунди.

**3. Навіщо «квитки» (`[i64; 3]`), і що буде, якщо не відписатися від старої сесії?**
Квиток (token) — це номер підписки, за яким від неї відписуються. Без відписки обробники старої сесії продовжували б спрацьовувати: зайві оновлення, «витік» пам'яті і плутанина між плеєрами.

**4. Чим `.join()` відрізняється від `.await`? Чому в окремому `std::thread` можна блокувати?**
`.join()` зупиняє потік, поки операція не завершиться. `.await` «відпускає» потік на час очікування, і він може робити іншу роботу. Наш медіа-потік існує лише для цієї задачі — нікому більше він не потрібен, тож блокувати його нормально.

**5. Навіщо ділити `Duration` на 10 000 і віднімати `WINDOWS_TO_UNIX_EPOCH_MS`?**
Windows рахує час у «тиках» по 100 наносекунд: 10 000 тиків = 1 мс. І рахує від 1 січня **1601** року, а JS (`Date.now()`) — від 1 січня **1970**. Віднімаємо різницю, щоб час був у тих самих одиницях, що й у JS.

### Крок 7 — UI плеєра

**1. Чому `media_control` — `async fn`? Що, якби вона була звичайною з `.join()`?**
Звичайні (синхронні) команди Tauri виконує в головному потоці, який малює вікна. `.join()` там «заморозив» би інтерфейс, поки Windows виконує дію (і міг би призвести до взаємного блокування). `async`-команда виконується у фоновому пулі потоків.

**2. Що отримає JS, якщо Rust поверне `Err("плеєр не підтримує цю дію".to_string())`?**
Відхилений Promise: `await invoke(...)` кине помилку з цим текстом, її можна зловити в `try/catch`.

**3. Що буде з `invoke("media_control", { action: "stop" })`?**
Варіанта `stop` в `enum MediaAction` немає, тож serde не зможе розібрати аргумент. Tauri поверне помилку ще **до** виклику функції — Rust-код не виконається.

**4. Навіщо `map_err` після всього `match`, а не в кожній гілці?**
`match` повертає один і той самий тип з будь-якої гілки — `Result` з асинхронною операцією. Тож перетворити помилку можна один раз для всього значення, без повторення в кожній гілці.

**5. Чому прогрес-бар рахується у фронтенді?**
Щоб не гонити дані з Rust кожні пів секунди. Rust надсилає позицію і момент заміру лише при змінах, а фронтенд сам «докручує» прогрес — плавно і без навантаження.

### Крок 8 — HTTP-сервер для Claude Code

**1. Навіщо `AgentServer` у `Arc`? Хто ще тримає на нього посилання?**
Його одночасно використовують сервер axum (кожен HTTP-запит — окрема задача) і Tauri: стан `AgentHandle` для команд `agent_respond` і `agent_info`. `Arc` дає спільне володіння: дані живуть, поки є хоч одне посилання.

**2. Чому для рішення `oneshot`, а не `mpsc`, як у кроці 6?**
На кожен запит дозволу буде рівно **одна** відповідь. `oneshot` — канал саме на одне повідомлення. `mpsc` — для потоку багатьох повідомлень (як сигнали медіа).

**3. Що станеться з записом у `pending`, якщо Claude Code обірве з'єднання через 3 секунди?**
axum знищить задачу-обробник, разом з нею знищиться «сторож» `PendingGuard`, і його `Drop` прибере запис з таблиці та надішле фронтенду `agent:permission-closed` — кнопки зникнуть.

**4. Чому `PERMISSION_TIMEOUT` (55 с) має бути меншим за `timeout` hook (60 с)?**
Щоб ми встигли відповісти самі (порожньою відповіддю → питання в терміналі) **до** того, як Claude Code обірве запит. Інакше відповідь острова могла б загубитися.

**5. Чому в `shorten` рахуємо `chars()`, а не байти?**
У UTF-8 українська літера займає 2 байти. Якщо обрізати рядок посередині літери, Rust панікує (і текст зіпсувався б). `chars()` рахує саме символи.

### Крок 9 — Claude Code в острові

**1. Чому острів під час запиту дозволу «закріплюється» розкритим?**
Щоб запит не зник, коли курсор пішов: на нього треба відповісти, інакше Claude Code чекатиме. Тому `pin()` не дає острову згорнутися, поки запит не закриється.

**2. Навіщо черга `queue`, і що, якщо дві сесії Claude Code попросять дозволу одночасно?**
Черга показує перший запит, а після відповіді — наступний. Без черги другий запит «перезаписав» би перший, і перший висів би до таймауту.

**3. Чому для `PermissionRequest` таймаут 60 с, а для решти 5 с?**
Запит дозволу чекає твого рішення (до 55 с). Решта подій — лише інформація: якщо острів раптом «завис», Claude Code не повинен гальмувати довше 5 с.

**4. Що отримає Claude Code, якщо натиснути «У терміналі»?**
Рішення `ask` → `agent.rs` повертає `200` з **порожнім** тілом → «рішення немає» → Claude Code показує звичайний запит дозволу в терміналі.

**5. Чому токен прихований, і чому `settings.json` з токеном не можна комітити в публічний репозиторій?**
З токеном будь-яка програма на цьому комп'ютері могла б надсилати острову фальшиві події. А якщо токен потрапить у публічний репозиторій, його побачать усі. Тому за замовчуванням він показаний крапками.

### Крок 10 — автозапуск і реліз

**1. Чому стан автозапуску читається з Windows (`isEnabled()`), а не з `settings.json`?**
Справжній автозапуск — це запис у реєстрі. Його можна вимкнути й поза програмою (Диспетчер завдань → «Автозавантаження»). Якби ми зберігали «так/ні» у своєму файлі, перемикач міг би показувати неправду.

**2. Чому вікно налаштувань на вимогу економить пам'ять?**
Кожне вікно WebView2 — окремий процес-renderer (~25 МБ), навіть приховане. Вікно, створене лише коли потрібне і знищене після закриття, цього процесу не тримає.

**3. Навіщо однакові `additionalBrowserArgs` для обох вікон?**
Усі вікна програми ділять один процес браузера WebView2 (одне «середовище»). Якщо друге вікно попросить інші аргументи, середовище не зможе їх виконати — і вікно не створиться.

**4. Як `pointerdown` + 500 мс захищають від випадкового схвалення?**
Рішення приймається лише якщо **натискання почалося вже на поточному запиті**. «Фантомний» клік, коли новий запит з'явився під курсором після попереднього кліку, такого натискання не має — і ігнорується. Плюс перші 500 мс після появи запиту кнопки не реагують зовсім.

**5. Що відбудеться після `git push origin v0.1.0`?**
GitHub побачить тег `v*` і запустить `release.yml`: на віртуальній Windows-машині встановить Node і Rust, збере `.msi` і `.exe` через `tauri-action` і створить GitHub Release з цими файлами.
